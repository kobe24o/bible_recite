# 灵修学习数据、任务状态与排行榜设计

## 目标

将每日灵修纳入学习数据和排行榜，并使今日页与每日提醒能准确反映灵修是否完成。实现必须保持本地优先、低网络请求、无笔记内容上云，并保留未来替换 Supabase 后端（例如 Cloudflare）的空间。

## 已确认的规则

- 只在用户进入**当天的灵修经文阅读页**后开始计时；打开灵修详情页、查看介绍或停留在笔记编辑区不计入阅读时长。
- 离开经文页、应用进入后台、失焦或锁屏时停止计时；恢复前台后才继续。不会把后台时间计入。
- 某日累计有效阅读时间严格超过 60 秒，或该日存在非空灵修笔记，即完成一次灵修；每个自然日最多计一次。
- 完成是当日参与事实：一旦达成，之后删除或修改笔记不回退完成次数、连续天数或排行榜累计数据。
- 只有当天的阅读和当天的笔记可以完成今天任务；历史灵修页不用于补记过去的排行数据。
- 灵修数据包括累计灵修次数、累计灵修时长、当前连续灵修天数、最高连续灵修天数。
- 排行榜仅展示会发生排名变化的指标；灵修四项均纳入，注册时长等静态信息不纳入。

## 架构选择

选择“本地每日聚合 + 延迟快照上传”。

备选方案比较：

1. 本地每日聚合（采用）：每个日期只有一条聚合记录，页面退出或应用暂停时才落库；排行榜沿用已有脏标记和约 15 分钟上传节流，读榜沿用约 5 分钟缓存。
2. 云端阅读事件流：可保存每次阅读细节，但会造成高频请求、更多隐私数据和免费额度压力，因此不采用。
3. 仅从笔记推导：无法统计无笔记的阅读时长，也不能满足“超过一分钟即完成”，因此不采用。

该方案不上传笔记正文，也不上传逐秒事件。仅上传已聚合的四个排行榜数值，既适合现有 Supabase RPC，也可保持 `LeaderboardGateway` 抽象，未来替换为 Cloudflare 实现时不影响页面和本地统计。

## 本地数据与统计

在 SQLite 中增加按当地日历日唯一的灵修活动表：

| 字段 | 含义 |
| --- | --- |
| `date` | 本地自然日，主键 |
| `active_seconds` | 该日已累计的前台经文阅读秒数 |
| `completed_at` | 首次完成灵修的时间；为空表示尚未完成 |
| `updated_at` | 最近一次计时写入时间 |

`DevotionStats` 是独立于 `LearningStats` 的领域模型，包含 `devotionDays`、`totalSeconds`、`currentDayStreak` 与 `maxDayStreak`。累计次数与连续天数都只依据 `completed_at` 非空的日记录；总时长则包含所有实际记录到的有效前台阅读秒数。

存储库提供下列边界清晰的方法：

- `recordDevotionReading(day, activeSeconds)`：累计已结束的一段有效阅读时间；仅允许当天调用。
- `completeDevotionFromNote(day)`：当天保存非空笔记时，以幂等方式标记完成。
- `isDevotionCompleted(day)` 与 `getDevotionStats(now)`：供今日页、提醒、统计和排行榜读取。

阅读计时由一个专用会话跟踪器管理。它接收进入/暂停/恢复/退出事件，累计经过的前台秒数，只在暂停、退出或页面销毁时写入。会话跨越午夜时，在当日边界停止，避免将旧的灵修经文阅读记到下一天。每次实际数据变更会标记排行榜为脏，但不会直接发网络请求。

## 页面与提醒

### 灵修详情与经文阅读

`DevotionDetailScreen` 打开当天灵修的 `PassageScreen` 时附带灵修会话上下文。通用经文页仍可服务普通经文、计划任务和复习；仅带有该上下文的当天灵修阅读会启动追踪器。保存当天非空笔记后立即刷新灵修活动状态。

### 今日页

今日页读取灵修完成状态并将灵修卡片放入与其他任务一致的分组：

- 未完成：位于“待完成”，显示书本图标、`待完成` 状态和进入箭头。
- 已完成：位于“今日已完成”，显示绿色勾选；副标题说明完成来源（已读经超过 1 分钟或已记录灵修笔记）。

从灵修页返回后，今日页刷新状态；灵修也参与“今日全部完成”的判断。

### 每日任务提醒

每日提醒的待办总数为：待完成背诵任务 + 待完成艾宾浩斯复习 +（存在今日灵修且未完成时的 1 项）。提醒标题保持现有应用名称，正文改为“今天还有 N 项学习任务未完成”。灵修完成、笔记完成或应用恢复后会重新排程；所有事项完成时取消后续提醒。

## 学习数据和排行榜

统计页新增“灵修数据”区块，展示累计次数、累计时长、当前连续灵修天数与最高连续灵修天数。

排行榜按下列固定顺序排列，使同类连续指标相邻且名称清晰区分背诵与灵修：

1. 累计背诵次数
2. 已背诵不同经节
3. 累计背诵时长
4. 最高连续背诵天数
5. 当前连续背诵天数
6. 累计灵修次数
7. 累计灵修时长
8. 最高连续灵修天数
9. 当前连续灵修天数
10. 勋章数量
11. 答题正确率

`LeaderboardSnapshot` 扩展四个灵修聚合字段；构建器从 `DevotionStats` 注入这些值。既有刷新与缓存策略不变：本地更新标记为脏，上传至少间隔 15 分钟；读取单项排行最多每 5 分钟请求一次，缓存优先。

## Supabase 数据库与安全

新增迁移扩展 `public.leaderboard_score`：

- `devotion_days`
- `total_devotion_seconds`
- `max_devotion_day_streak`
- `current_devotion_day_streak`

前三项是单调累计值，不允许小于该用户此前已提交的数值；当前连续灵修天数允许下降。为每个新排行指标增加对应的降序索引。

私有 schema 中的快照提交函数与公开 wrapper 接受四个新字段，`read_board` 的允许列表和排序表达式支持四个新指标。已有十参数公开接口保留为兼容 wrapper：旧客户端提交快照时读取并保留该用户已有灵修聚合值，绝不以零覆盖新客户端的数据。

安全边界保持不变：

- 两个 `public` 排行榜表启用 RLS，用户仅能读取自己行；客户端没有直接插入或更新权限。
- 有权写入聚合值的函数位于未暴露的 `leaderboard_private` schema，使用固定 `search_path`、调用者身份检查和每用户事务锁。
- 公开 RPC 是 security invoker wrapper，且只向 `authenticated` 授权；匿名登录生成的认证用户可使用它。
- 不使用 service-role key，也不上传笔记或设备详细信息。

## 错误处理与一致性

- 计时写入失败不丢失可见笔记内容；页面显示操作失败并允许重新进入后继续记录。
- 云端同步失败只保留本地脏标记并按现有节流重试，排行榜继续显示本地数值和已缓存结果。
- 当次灵修写入与完成标记使用同一 SQLite 事务；重复的暂停、退出和笔记保存均幂等。
- 旧客户端与新客户端交替上传时，兼容 wrapper 保留新字段，累计榜单不会倒退。

## 验收与测试

按测试优先开发，覆盖以下证据：

1. 少于或等于 60 秒不完成、超过 60 秒完成、非空笔记完成、同日重复操作仍只完成一次。
2. 暂停/后台时间不累计，跨日阅读不记到次日，连续灵修的当前值与最高值计算正确。
3. 今日页在未完成和已完成之间移动灵修卡片，并更新提示文案与“今日全部完成”判断。
4. 每日提醒将未完成灵修计入数量，完成后不再创建提醒。
5. 统计页和排行榜快照包含四项灵修指标，排行榜 chip 顺序和显示名称符合本设计。
6. Supabase 迁移测试验证新字段、受限指标读取、累计值不可回退、旧接口不覆盖灵修数据，以及 RLS/RPC 权限。
7. 运行相关聚焦 Flutter 测试、完整 Flutter 测试套件、数据库迁移检查，并以认证用户对新排行榜指标执行真实查询。
